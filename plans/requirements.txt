Stress:

Stress is derived from HRV over a time window, so it is not sampled at HR frequency.

On many Garmin wearables, stress values are closer to “one value per minute” (sometimes irregular), and each value corresponds to a computation window preceding the timestamp.

In practice: you see far fewer stress_level_mesg entries than HR samples.

So they do not share a common, fixed frequency; stress is much sparser and derived.

Temporal relationships between messages
Conceptually, a FIT activity file is a timeline of messages, not a set of relational tables.
​

file_id, activity, session, lap, event messages:

Provide structure and metadata: total durations, start/stop times, lap boundaries, sport type, etc.

They help you understand segments and context but are not dense time-series.

record_mesg:

Your main high‑resolution time-series for an activity (timestamped samples of HR, speed, position, etc.).
​

Can be thought of as “primary track” during the workout.

monitoring_mesg and stress_level_mesg:

Background streams: steps, all-day HR, calories, and stress/Body Battery if present.
​

They coexist in the same file (e.g., daily file) or separate files and share the global time axis but not the same cadence.

Logically: everything is tied together by timestamp, not by explicit keys/joins. The “relationship” is time alignment.

Event vs time-series view
You can view FIT logging as:

Event-based: each message is an event with a timestamp and fields.

Time-series: some message types (e.g., record_mesg) behave like regular time-series sampled at roughly constant intervals.

In reality it’s a mixed model:

Activity records: quasi-regular time-series.
​

Stress: irregular event stream (new value when a stress computation is ready).

Monitoring: lower-frequency, sometimes aggregate; irregular if device optimizes battery.
​

This is why treating it purely as relational data (joining by index) causes trouble: the “primary key” is really the timestamp plus message type.

Should you resample to a common time grid?
This depends on your use case.

Resampling to a common grid (e.g., 1 s, 5 s, or 60 s) is useful when:

You want to feed the data into models that expect fixed-step time-series (RNNs, CNNs, classical TS models).

You need a single row per time step with aligned columns for HR, stress, speed, etc.

Common approach:

Choose a base resolution that matches the densest source you care about:

For workouts: often 1 s or 2 s.

For all‑day analysis: often 60 s.

For each metric:

Map each message to the grid using its timestamp.

Use forward-fill / last observation carried forward for piecewise-constant metrics (stress level is usually interpreted this way within its validity window).

Use interpolation (e.g., linear) for “smooth” continuous metrics like HR or pace, if you need continuity.

Explicitly track gaps where data is absent (e.g., NaNs or flags) so you don’t invent information over long missing periods.

Resampling gives you a clean matrix but at the cost of lossy transformation and some modeling assumptions.

Should you preserve the raw event stream?
You almost always want to keep the raw event stream as your ground truth and derive resampled views from it.

Reasons:

FIT semantics live in the raw events (e.g., event messages for pause/resume, laps, auto‑laps).
​

Vendor-specific metrics (developer fields) may not map cleanly to a simple grid.

For some analyses (e.g., “what stress value was present when this event occurred?”), working directly with the event stream plus nearest-neighbor lookup is more precise.

A good pattern:

Store one row per message (message type, timestamp, and all fields).

Build views:

Activity-channel view: only record_mesg plus derived fields.

Monitoring-channel view: monitoring_mesg and related.

Stress-channel view: stress_level_mesg / stress-related fields.

Then build resampled tables on demand.

Correlating metrics with different sampling rates
Key idea: time alignment by timestamp, not by index.

Practical strategies:

Nearest neighbor / window lookup (event-centric)
For each “anchor” event (e.g., each record_mesg), find stress messages whose timestamps fall within a window around it (e.g., ±30 s) and:

Pick the nearest stress sample.

Or compute a windowed statistic (mean or median stress in that window).

This keeps HR at native resolution and attaches the “most relevant” stress value.

Putting it together for your workflow
Applied to your four core issues:

Message frequency

HR: denser, often ~1 s in activities, coarser all day.
​

Stress: sparser, roughly once per minute or irregular events.

They are not logged at the same interval and are not 1:1.

Message relationships

Related via time and, for structure, via activity/session/lap metadata, not via relational keys.

Think: multiple asynchronous channels on a shared timeline.

Data streaming model

Mixed: quasi-regular time-series (record), plus asynchronous events (stress, monitoring, pauses, laps, etc.).

What to store and how to analyze

Store raw events (one row per message).

Build time-aligned views by:

Resampling to a grid when you need matrices.

tell me what the vivosmart 5 would use
For the vívosmart 5, you can assume it behaves like other recent Garmin wearables: continuous optical HR, all‑day stress based on HRV, and FIT logging that separates activity data from background monitoring.

What sensors and metrics it logs
The band has an optical heart rate sensor running 24/7, plus accelerometer and SpO₂ (Pulse Ox) for sleep and respiration, and it computes stress level and Body Battery from heart‑rate variability.

It tracks HR, steps, calories, sleep stages, respiration, Pulse Ox, and all‑day stress level continuously, then exposes these in Garmin Connect as time‑series graphs and summaries.

How heart rate is sampled
HR is effectively always on: the device monitors heart rate 24/7, with higher sampling during workouts and somewhat lower (but still frequent) sampling at rest to save battery.

During a workout profile (run, walk, bike, etc.), HR is used for workout stats (zones, calories, intensity minutes) and will show up as dense, near‑per‑second samples in activity FIT files; outside workouts, HR goes into all‑day monitoring streams.

How stress is computed and logged
All‑day stress monitoring uses a Firstbeat‑style algorithm based on HRV, similar to other current Garmin trackers; it is explicitly described as “all‑day stress monitoring” on the vívosmart 5.

In practice that means fewer, derived samples (roughly minute‑level) rather than per‑beat or per‑second; the watch suspends this during tracked workouts and resumes in daily life, and Connect shows it as a continuous stress graph across the day.

What this implies for FIT / data handling
For your purposes, assume vívosmart 5 writes:

HR: dense samples during activities (record_mesg in activity files), plus lower‑frequency all‑day HR in monitoring streams.

Stress: sparse stress events/time‑series (often about once per minute) in stress/monitoring channels tied to the same clock, not the same cadence as HR.

So for vívosmart 5 data workflows, the same guidance from before applies: treat HR and stress as asynchronous time‑series on a shared timeline, keep the raw event stream, and when you need them together, align by timestamp (nearest neighbor or resampled grid) rather than expecting matching indices.

how can I identify what is what when reading fit binaries
Every FIT file tells you “what is what” using a combination of IDs and a profile table; practically you decode it by mapping numeric message/field IDs to human‑readable names from Garmin’s FIT profile, then decoding timestamps, enums, and scaling.

Big picture: how FIT labels things
Each FIT file is a sequence of messages, and each message has:

A global message number (e.g., 20 = record, 34 = lap, etc.).

Several fields, each with a field number, base type, and optional scale/offset and units defined in the profile.

The official mapping from numbers → names (message names, field names, enum values, units) is in the Garmin FIT SDK’s Profile.xlsx (and mirrored in many libraries).

So “identifying what is what” is really “looking up these numeric IDs in the profile.”

Step 1: identify the file type
Every FIT file contains a file_id message (global ID for file_id).
​

The type field inside file_id says what kind of file it is, for example:

activity (typical workout).

monitoring (all‑day data).

device or others.

Once you know the file type, you know which message types are expected:

Activity file: file_id, activity, session, lap, event, record, etc.

Step 2: follow definition messages
FIT uses definition messages that come before the actual data (data messages):

A definition message says:

“Local message number X corresponds to global message Y (mesg_num).”

“Here are the fields that will appear for this local message: field numbers, base types, sizes.”

Every subsequent data message with that local number is interpreted using that definition:

Local 0 might be record with fields like timestamp, position_lat, heart_rate, etc.

Local 1 might be lap, with start_time, total_elapsed_time, etc.

So when parsing raw FIT bytes you:

Read a record header, see if it’s a definition or data.

If definition: store “local 0 → mesg_num 20 (record) with fields [timestamp, distance, heart_rate, …]”.

If data: use that stored definition to decode the bytes into named fields.

Step 3: map global message numbers to names
To know that mesg_num = 20 means record (and 19 = lap, 18 = session, etc.), you use the profile:

Garmin’s Profile.xlsx lists:

Each global message number with its message name (e.g., record, lap, session, event, monitoring, stress_level, etc.).

For each message, each field number with field name, type, scale, offset, and units.

Enum tables: e.g., event field values, sport values, manufacturer IDs.

Libraries like FITfileR, some Java/Python decoders, and various viewers embed this profile so they can show “record.heart_rate = 145 bpm” instead of raw bytes.

In practice, you rarely hand‑maintain this mapping; instead you:

Use an existing decoder library for your language that includes the FIT profile.

Or directly load Profile.xlsx and generate code/tables from it.

Step 4: identify fields inside each message
Once you know “this data message is a record,” you still need to know what each field number means:

The definition message tells you the field numbers present; the profile maps them to names like:

0 → position_lat, 1 → position_long, 2 → altitude, 3 → heart_rate, etc. for record (numbers are just an example).

The profile also tells you how to interpret the raw values:

Scale/offset (e.g., distance stored in 1/100 m, altitude in 1/5 m, lat/long in semicircles).

Units (meters, seconds, beats per minute, etc.).
​

Some fields are enums, so you translate codes to labels:

For example, an event field might be 0 = timer, 9 = lap, 22 = battery_low, etc.
​

So identification = “local → global message number → message name; field number → field name, type, units.”

Dealing with “unknown” or undocumented stuff
You will see:

Global message numbers that aren’t in an older Profile.xlsx (new device/firmware).

Field numbers inside known messages that aren’t in the profile.

Enum values not yet documented.

For these:

You can still keep the raw bytes and the fact that they exist; just label them as unknown fields.

Tools like FIT File Viewer and community spreadsheets extend the official profile with newly observed IDs so you can progressively label more items.
​

This is normal; you don’t have to understand every field to make good use of record/monitoring/stress messages.

Practical workflow you can use
Given your context (already thinking in terms of message types):

Use a library or your own parser to:

Read the file.

Enumerate all message types and their fields for a sample file.

For each message:

Map mesg_num → message name via the profile.

Map field numbers → field names, types, and units via the profile.

In your DB or analysis:

Keep a column for mesg_num and local_mesg_num so you always know what type of row it is.

Optionally pivot out common messages (e.g., all rows where mesg_num == record) into dedicated tables/views.

For metrics like heart rate and stress:

Identify which message types and field names carry them (e.g., record.heart_rate, monitoring.heart_rate, stress_level.stress_level).

Use timestamps as your primary join key across message types.

If you paste a short hex dump or a small decoded snippet (e.g., the first few definition and data messages from your parser), I can walk through it line‑by‑line and show exactly how to tell which rows are record, monitoring, or stress_level and which fields are which.
